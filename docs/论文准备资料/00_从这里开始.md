# 从这里开始

> 这不是论文正文。它的作用是告诉协作者每份资料的用途、可信等级和维护人，避免把早期素材或计划误写成已经完成的结果。

## 这次可以审阅什么

这套资料目前足够用于审阅：

- 研究问题是否明确；
- PDE、损失和结构化源项是否自洽；
- 代码实现方向是否与数学表述一致；
- baseline、消融和评价指标是否合理；
- 正式 IEEE 论文应如何分工和组织。

目前还不够用于审阅最终性能或直接投稿，因为以下内容尚未完成：

- 正式实验代码与统一输出链路；
- 合成数据、U-Net-small、FFT 和 PINN 的最终结果；
- 三个随机种子的统计；
- 最终锁定的超参数与代码 commit；
- IEEE 模板中的正式摘要、结果、讨论和结论。

因此，这次请把它称为**方法与实验方案审阅材料**，不要称为“论文初稿”。

## 请审阅者重点回答

### 请学长重点看

1. screened Poisson 形式和 $I_{city}$ 的建模定位是否表述得足够谨慎？
2. 当前未显式施加边界条件，是否需要补边界损失，或在论文中说明即可？
3. 固定 $\alpha=0.5$、把重点放在 PDE 与可学习源点中心上是否合理？
4. `FFT-Gaussian / U-Net-small / PINN` 三种主对比是否足够且公平？
5. `DataOnly / CenterFixed / BrightInitFixed / BrightInitLearnable` 消融是否能回答核心问题？
6. 合成数据指标、真实图三图展示和失败案例设计是否还缺关键项目？

### 请文字负责同学重点看

1. 一句话方法定义是否容易理解，有没有仍需实现负责人解释的术语？
2. 摘要中哪些事实已经可以写，哪些结果必须留空等待实验？
3. IEEE 的 Introduction、Related Work 和 Method 是否还缺她需要的技术素材？
4. 是否存在容易被误写成“已证明”“严格物理模型”或“显著优于”的句子？
5. 后续每次技术更新希望以什么形式接收，避免口头同步遗漏？

## 推荐工作顺序

1. 写摘要、引言或方法前，先读[技术事实交接单](./02_实现与交接/技术事实交接单.md)。
2. 需要公式时，读[PIN 数学原理](./01_数学与方法/PIN数学原理.md)和[光污染物理约束的构造](./01_数学与方法/光污染方程简化步骤.md)，再与最终代码核对符号。
3. 写实验设置、结果和结论时，只按[论文实验计划](./03_实验/论文实验计划.md)中已经执行并保存的配置与结果填写。
4. [论文内容参考结构](./04_写作参考/论文内容参考结构.md)中的摘要、进度和预期成果均是历史素材，不直接复制到 IEEE 正式稿。

## 协作约定

- 推导与实现负责人负责确认：PDE、损失、网络、数据处理、训练配置、输出含义和实验状态。
- 文字负责人负责：摘要、引言、相关工作、结果叙述和 IEEE 排版，但不得把“计划”“原型”或“待验证”写成已证明结论。
- 每次代码或实验配置改变后，先更新技术事实交接单，再改论文正文。
- 不确定的说法先标记为“待确认”，不要为了让摘要完整而猜测。

## 正式 IEEE 稿的最小骨架

```text
Title / Authors
Abstract / Index Terms
I. Introduction
II. Related Work
III. Method
IV. Experimental Setup
V. Results and Discussion
VI. Conclusion
References
```

其中 `III. Method` 和 `IV. Experimental Setup` 应由实现负责人核对，`V. Results and Discussion` 只能使用实际运行产生的表格、曲线和图片。
